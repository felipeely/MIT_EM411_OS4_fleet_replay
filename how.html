How the numbers are calculated

Two programs share the same vehicle data. On the replay page, Model day shows the model's own view of one day: requests arrive evenly, every ride is the average 1.1 km, only the vehicles the availability rounds down to are in service and batteries are not tracked.

model.py is the fast model that scores millions of fleets with simple formulas. sim_day.py plays one day request by request, 200 times, to check the model. The replay page shows the simulation. Every formula below is taken from the code.

1. One vehicle

Each vehicle is a set of parts from the Appendix tables. Cost, weight, energy use, range, speed and charging time follow from the parts.

cost    = (chassis + battery + charger + autonomy) x $1000 + motor          [$]
weight  = chassis + battery + charger + motor + autonomy + seats x 100 kg   [kg, full load]
power   = nominal + 0.1 x (weight - chassis weight) + autonomy power        [Wh/km]
range   = battery kWh x 1000 / power                                        [km]
speed   = min( 700 x motor kW / weight , speed limit )                      [km/h]
speed_empty = same with the passengers removed from the weight

E-bikes take their speed from a power balance on flat ground, solved numerically:

0.8 x motor W  =  0.005 x m x 9.81 x v  +  0.5 x 1.2 x 0.5 x v^3        (v in m/s, capped at 20 km/h)

Charging uses a taper. The first 80% of the energy goes in at full charger power and the last 20% at 30% of it:

charge_h   = battery kWh / charger kW x ( 0.8 + 0.2 / 0.3 )
uptime_h   = range / speed
downtime_h = charge_h + 0.25 h
availability = uptime_h / ( uptime_h + downtime_h )

Worked example: reference shuttle C3/P2/G3/M2/A4. Cost $83,800. Weight 2,765 kg. Energy use 244 Wh/km, so a 100 kWh battery gives 410 km. Loaded speed 25.3 km/h and empty speed 32.2 km/h (the limit). Charging takes 2.44 h. Up-time is 16.2 h and down-time 2.69 h, so availability is 0.857.

2. Demand and party size

Demand comes from the Appendix B table in passengers per hour, constant inside each 2 hour block:

A party is 1 to 6 people with shares 60, 20, 10, 5, 3 and 2%, so the mean party is 1.77 people. One party rides together. A party larger than the seats uses more vehicles. For a vehicle with s seats the average load is:

p(s) = E[ party size ] / E[ ceil( party size / s ) ]        p(1)=1.0   p(2)=1.416   p(4)=1.686   p(6)=1.77

3. The fast model (model.py)

For every 2 hour block the model asks how many vehicles are in service, how many trips per hour they can move, and how long a passenger waits.

cycle time   T = d / speed  +  0.5 x d / speed_empty  +  2 x 60 s        [h]   (d = 1.1 km average trip,
                                                                       50% of trips return empty)
in service   c = floor( n x availability )                            (2.57 vehicles in service counts as 2)
capacity       = c x p(s) / T                                         [passengers/h]
requests     lambda = demand / p(s)                                   [trips/h]
busy vehicles  a = lambda x T          utilisation  rho = a / c

When the demand is shared by shuttles and bikes, it splits in proportion to their capacities. The wait is half the time between vehicles plus the drive of the nearest idle vehicle:

headway      = T x 60 / c                                             [min]
idle         = max( c - min(a, c), 1 )
pickup       = 1.3 x 0.5 x sqrt( 3.5 km2 / idle ) / speed_empty x 60  [min]
wait         = 0.5 x headway + pickup       if rho < 1,   else 30 min (capped)

The 1.3 is the detour factor from straight line to street. The nearest of idle vehicles spread at random over 3.5 km2 is on average 0.5 x sqrt(area / idle) away. The rush-hour test divides every speed by the traffic factor (shuttles 0.58, bikes 0.85) in the blocks that start at 08, 10, 12, 14 and 18.

Worked example, shuttles alone carrying a 150 people/h block. T = 1.1/25.3 + 0.5 x 1.1/32.2 + 0.0333 = 0.0939 h. Ten shuttles give c = floor(8.57) = 8. Requests are 150/1.77 = 84.7 per hour, so a = 7.95 and rho = 0.99. Headway is 0.0939 x 60 / 8 = 0.70 min. Only one vehicle is idle, so the pickup drive is 1.3 x 0.5 x sqrt(3.5) / 32.2 x 60 = 2.3 min. Wait = 0.35 + 2.3 = 2.6 min.

Average wait is the demand-weighted wait over all blocks. Peak wait is the average wait in the busiest 2 hour block, and it is the one tested against the 5 minute requirement.

MAU  = 0.15 x U(volume) + 0.25 x U(throughput) + 0.35 x U(wait) + 0.25 x U(availability)
fleet cost = n_shuttles x shuttle cost + n_bikes x bike cost         (vehicles only)

Requirements checked: wait of the peak block at most 5 min, longest ride (2.1 km at the loaded speed, slowed by traffic in the rush test) at most 7 min, volume at least 1,500 per day, peak 150 and off-peak 50 passengers per hour.

5. The day simulation (what the replay shows)

The simulation does not use averages. It plays the day request by request.

1. Requests arriveParties arrive at random times at the hourly rate of the demand table divided by 1.77 (Poisson). Each party size is drawn from the 60/20/10/5/3/2 shares.
2. Pick a vehicleAmong idle vehicles, the one with the lowest battery takes the ride, so charging is staggered. If none is idle the request waits for the first vehicle to be free.
3. Drive to the passengerDistance is 1.3 x 0.5 x sqrt(3.5 / idle vehicles) at the empty speed. This drive is part of the wait and uses energy.
4. RideLength is uniform between 0.2 and 2.0 km. Boarding and drop-off take 60 s each. With 50% chance the vehicle then drives back empty.
5. ChargeBelow 20% battery the vehicle goes to charge until full, at the tapered charging time.
6. CountWait = time in line + pickup drive. Run 200 days with seeds 1000 to 1199 and average.

Two dispatch rules. The Dispatch switch on the replay page chooses between them. Standard is the rule above: a vehicle that is driving back empty cannot be reassigned until it arrives, so it is not counted as available. Smart counts a vehicle that is on its empty return (and is not due to charge) as available. If it is picked for a waiting passenger it keeps the part of the return it already drove, loses the rest (and gets that energy back), and drives from where it is to the passenger. Everything else is identical: same demand, same random draws, same batteries, same charging. Smart only changes who can be sent. The fast model has no dispatch rule, so its numbers do not change.

Bikes on campus paths. The Bikes switch lets e-bikes use the footpaths and crosswalks of the City of Cambridge GIS data (the Sidewalk_Centerlines layer, types footpath and crosswalk) in addition to the streets. Shuttles stay on the streets, and the bike speed does not change. The simulation has no geography, so the footpaths enter as a path factor: for 500 random buildings inside the service area, the route from building to building is measured on the street network and on the street + path network (the bike can always still choose the street route), for trips of 0.2 to 2.0 km. On average the bike route is 0.956 of the street route (0.946 for the shortest trips, about 0.96 for the rest), and 26% of the trips are more than 5% shorter. Every bike pickup, ride and empty return in the simulation is multiplied by 0.956, the demand split between shuttles and bikes uses that shorter bike cycle, and everything else is identical (same random draws). On the map the bikes follow the real footpaths. The fast model does not know about paths, so its numbers do not change.

wait   = ( start of ride - request time ) + pickup drive
energy = energy - power x ( ride km x ( 2 if empty return else 1 ) + pickup km ) / 1000
charge when energy < max( 4 km x power / 1000 , 0.2 x battery )

The map in the replay is added afterwards. Each pickup, ride and empty return is placed on real Cambridge streets whose network length matches the simulation's distance, and the timing is the simulation's own. The replay was checked to give the same waits, trips, charging and passenger counts as the simulation.

6. Why the model and the simulation differ

The model sees a smooth, even flow of requests. The simulation has random bunching, so a queue forms whenever several parties arrive within a short time, especially when utilisation is close to 1. For the reference fleet the model gives a peak wait of 2.6 min, the simulation 9.5 min. That is why the reference fails the 5 minute requirement in the simulation. The model is still used to search the design space because it is millions of times faster, and the simulation is used to confirm the short list.
